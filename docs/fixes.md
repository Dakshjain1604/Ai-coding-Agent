## Robustness test battery (tool-parser + full agent loop)

Built a shared `FakeProvider` harness (`tests/helpers/agent-test-harness.ts`) that seeds the real `ProviderFactory`/`ModelRouter` chain so tests drive `UniversalAgent.execute()` through its actual production path. 69 independently-designed tests (not retrofitted to existing behavior) found 5 real bugs:

- **Stale `KNOWN_TOOLS` list** in `tool-parser.ts` — missing most real tools, included some that never existed. Now threads the agent's actual registered tool names through instead.
- **Two of four parser strategies had no tool-name validation at all** — an ordinary bare-fenced code block with a one-word first line was silently treated as a bogus tool call. Gated all four strategies uniformly.
- **`parseJsonObject`'s regex truncated at the first closing brace** — broke on any nested params object, i.e. almost every real tool call (`{"tool": X, "params": {...}}` is already nested). Replaced with a brace-balanced scanner. This had been silently broken the whole time — an earlier test suite's assertion coincidentally passed either way, masking it.
- **`UniversalAgent.execute()` silently discarded the mode passed to its constructor** unless the task also carried `metadata.mode` — broke `spawn_subagent` entirely, since `ParallelOrchestrator` builds each pipeline step with an explicit mode but subtasks don't carry that metadata field.
- **Duplicate `startConversation()` call** orphaning a conversation row per task (the cause of the real `.claude/memory.db`'s 26-conversations/0-turns state).

## Phase 3: Failure classification (architecture-optimal.md item 18)

Resolves the "known limitation" below. New `src/core/agents/failure-classifier.ts` — classifies caught LLM-call errors (structured status code when available, message-pattern matching otherwise) so the retry loop can tell a transient failure (429/5xx/network — worth a backoff retry) from one that will never succeed on retry (413/401/400/404 — skip straight to a bounded provider-fallback attempt) from a local bug (TypeError/etc. — neither retry nor fallback helps, fail fast). Live-verified: the same task that used to waste ~6s of blind backoff on a 413 now fails in ~650ms. 112 independently-designed tests (98 unit + 14 integration) — writing them caught a bug in the integration itself: the classifier's `shouldChangeStrategy` field was defined but never actually checked, only `retryable` was, so internal errors were still triggering a wasted fallback attempt.

## Sub-agent spawning hardening (`spawn_subagent` / `ParallelOrchestrator`)

The mode-desync bug found in the prior phase had already proven this subsystem was silently broken, so it got the same code→iterate→test treatment. Fixed 6 real bugs, verified each via live reproduction before and after:

- **Mode-leak via metadata spread.** `ParallelOrchestrator` spread the parent task's whole `metadata` (including its own `mode`) into every subtask's metadata. Since `UniversalAgent.execute()` treats `task.metadata.mode` as always-wins, a parent run with `--mode=code` silently forced every spawned subtask into `code` mode regardless of what `plan.mode` actually asked for. Fixed by excluding `mode` from the spread.
- **Uncaught crash on an invalid `task.metadata.mode`.** A bare `as AgentMode` cast let any string reach `setMode()`, which threw `toolNames is not iterable` the moment `TOOL_SETS[mode]` came back `undefined`. Added `isValidAgentMode()` (single source of truth in `system-prompts.ts`) and validate before ever calling `setMode()`; an invalid mode now logs a warning and falls back to auto-detection (or the agent's pinned mode) instead of crashing.
- **`narrowChildTools` failed open on an empty `parentToolNames`.** The one real caller never passes an empty array today, but the code treated "no parent tool info" as "skip narrowing entirely" — a latent violation of "a child can never have more capability than its parent granted it." Fixed to fail closed.
- **Confusing raw `TypeError` on malformed `subtasks` entries.** A `null`/bare-string/missing-description entry surfaced as `Cannot read properties of null (reading 'mode')` — caught, but useless for the model to self-correct from. Now validates each entry explicitly and reports exactly which indexes are malformed and why. Also added `MAX_SUBTASKS_PER_PIPELINE = 10` and a bounded `boundedContext()` (16k chars) — each subtask's description previously accumulated every prior subtask's full output with no cap.
- **Real bug found by the e2e test battery, not by code reading: `execute()` unconditionally re-ran `setMode()` even when the mode wasn't changing.** `setMode()` unconditionally does `tools.clear()` + repopulate from that mode's *default* tool set. A spawned child (`new UniversalAgent(plan.mode)`) had `shell_exec` correctly stripped by `narrowChildTools()` immediately after construction — then `execute()` called `setMode()` with that same mode anyway and silently re-granted it, undoing the restriction the moment the child actually ran. Caught live: an e2e test asserting a restricted tool call never executes instead hung on a real interactive permission prompt for `shell_exec` from inside a "narrowed" child. Fixed by only calling `setMode()` when the mode is actually changing.
**Test battery: 71 independently-designed tests** across `tests/unit/subagent.test.ts` (5→21), `tests/unit/system-prompts.test.ts` (19, new), `tests/unit/subagent-tool.test.ts` (23, new), `tests/unit/agents.test.ts` (+8 mode-validation regression tests, driven through the real `FakeProvider` harness rather than internal mocks), and `tests/e2e/subagent-spawn.test.ts` (5, new — real tool-call-parsed `spawn_subagent` invocations through the full provider chain). The tool-narrowing bug above was caught by exactly this kind of test: it would have been invisible to a test that called `ParallelOrchestrator.narrowChildTools()` directly rather than driving a real spawned child through its actual `execute()` path.

## File-mutation safety net (RollbackManager wiring)

Audited what happens when the agent writes something wrong. Finding: `buildTaskSystemPrompt()` falls back to `process.cwd()` as the output directory whenever `task.metadata.outputDir` isn't set — which is every real call site in this codebase today, despite the "sandbox-safe" design principle in CLAUDE.md — so `file_write`/`file_delete` operate directly on the real project tree in normal use. There was already a fully-built `RollbackManager` class (`utils/git-rollback.ts`) with snapshot/rollback/diff-preview methods and **zero call sites anywhere in `src/`** — a safety net that was built and then never wired up, same shape as the `conversationId` bug from the memory phase.

- **Wired `RollbackManager` into the real file-mutating tools**, and closed the gaps that made the original class impractical for how this CLI actually runs (most invocations are a single short-lived process): snapshots are now bounded in-memory (last 5 per file) *and* persisted to disk as a single latest-backup-per-file under `.claude/rollback-backups/`, so `coding-agent rollback <path>` works even in a brand-new process restoring after a prior run.
- **New `file_restore` agent tool** — lets the agent self-correct mid-task ("that write was wrong, undo it") instead of trying to manually reconstruct prior content. Gated the same "prompt" permission level as `file_write`/`file_delete` (restoring is still a real mutation).
- **New `coding-agent rollback` CLI command** (`--list` / `<path>` with a diff preview + confirmation) and a matching interactive-mode `/undo` command, both mirroring the existing `memory`/`config` dual-surface pattern.
- **Real bug found while building the e2e test for this, not by code reading: two parallel, drifting implementations of `file_write`/`file_delete`/`file_read`/`file_list`.** One lived in `builtin.ts` (registered first, the one actually reachable through the tool registry — richer, with post-write auto-formatting and a dependency-graph audit hook) and a second, dead duplicate lived in `file-system.ts` (only reachable by calling `createFileSystemTools()` directly, which nothing in the real registration path does for those four names — see the `FS_EXTRAS` allowlist that quietly excluded them). The rollback snapshot() call was first added to the dead copy in `file-system.ts` and silently never ran in the real agent loop — caught because an e2e test drove a real `file_write` → `file_restore` sequence through the actual tool registry and the restore came back "no backup found." Fixed by deleting the four dead duplicates from `file-system.ts` entirely and wiring the snapshot calls into `builtin.ts`'s real `fileWrite`/`fileDelete` instead, rather than patching the unreachable copy.
- Also fixed a small dangling reference: `SYSTEM_PROMPTS.test` told the model it had a `coverage_report` tool, which was never implemented anywhere (a stale reference `tool-sets.ts` had already been corrected to note, but the prompt text itself was never updated).

**Test battery: 59 new tests** — `tests/unit/git-rollback.test.ts` (34, new — `RollbackManager` itself: bounded history eviction, LIFO in-memory rollback, disk-backed fallback across simulated process restarts, `listBackedUpFiles()`/`peekBackup()`/`generateDiffPreview()`, corrupt-backup-file resilience, singleton seed-before-first-use semantics), `tests/unit/file-system.test.ts` (20, new — the real `fileWrite`/`fileDelete` wiring plus `file_move`/`file_restore`), `tests/unit/permission-system.test.ts` (+2 — `file_restore`'s permission rule), `tests/e2e/agent-loop.test.ts` (+3 — a real `file_write` → `file_restore` sequence driven through actual tool-call parsing, not direct handler calls, which is exactly what caught the dead-duplicate bug above).

## Command injection across the tool layer (git/shell/search tools)

While auditing what happens when the agent writes something wrong (the file-mutation phase above), a second dead-code file turned up: `git-operations.ts`'s `createGitTools()` — a full implementation of `git_branch`/`git_checkout`/`git_reset`/`git_remote`/`git_push`/`git_pull` — had **zero call sites anywhere**, same shape as `RollbackManager` before it. The agent had no way to create/switch branches, push, pull, or reset at all; only `git_status`/`git_diff`/`git_log`/`git_add`/`git_commit` (a separate, individually-registered implementation in `builtin.ts`) were reachable.

Reading both implementations before wiring the dead one up surfaced something much more serious: **every one of these tools — including the ones already live and registered — built its shell command by interpolating user/model-supplied values directly into a string passed to `exec()`**, which runs through `/bin/sh -c "..."`. Quoting (where attempted at all) only escaped literal `"` characters; backticks, `$(...)`, `;`, `&&`, and `|` all still execute as their own command regardless of quoting. **Confirmed exploitable with a live PoC against the already-registered, in-production `git_commit` tool**: `gitCommit.handler({ message: "pwned\`touch /tmp/PWNED\`" })` created a real file on disk. The same pattern was present in `gitLog`/`gitAdd`/`gitDiff` (all in `builtin.ts`), the dead `git-operations.ts`, `shell_which`, `process_list`, `logs_read`, `test_run`'s pattern param, `code-search.ts`'s `grep` tool, and `formatter.ts`'s prettier invocation — a systemic issue across essentially every "structured, narrower-than-shell_exec" tool wrapper, not an isolated bug. (`shell_exec` itself is intentionally exempt — running an arbitrary command IS its declared purpose, mitigated by permission gating + `DEFAULT_SHELL_PREFIX_RULES`, not string-escaping.)

- **Fixed every vulnerable handler** by switching from `exec()`/string-interpolation to `execFile()` with an argv array (`git`, `["commit", "-m", message]`, etc.) — no shell is ever invoked, so this injection class is structurally impossible regardless of what characters a value contains, not just harder to trigger.
- **`process_list`'s `filter` and `logs_read`'s `path`/`filter`** no longer shell out to `grep`/`tail`/`powershell` at all — filtering/tailing now happens in JS after a plain `execFile("ps", ["aux"])` (process_list) or a direct `readFileSync` (logs_read). Also fixes a real cross-platform inconsistency (the old Windows branch used a differently-shaped, equally-injectable PowerShell string) and a line-counting bug found while testing this: a trailing newline in the log file used to produce one fewer real line than requested (a phantom blank "line" from `split("\n")` wasn't being stripped before the tail slice).
- **`code-search.ts`'s `grep` tool rewritten as pure JS**, reusing the same walk-and-regex-match approach `search_content` already used safely, rather than reinventing an execFile-safe shell grep invocation — avoids the whole platform-inconsistency problem (BSD vs GNU grep flags) for free, and eliminates the shell dependency entirely rather than just making it safer.
- **`git-operations.ts` rewritten and wired up**, with the five names that overlap `builtin.ts` (`git_status`/`git_diff`/`git_log`/`git_add`/`git_commit`) deleted from it entirely rather than kept as a second implementation — recreating the exact duplication trap from the file-mutation phase, for the exact same tool-registration reasons, was the obvious failure mode to avoid here. `git_branch --delete` defaults to git's safe `-d` (refuses on unmerged commits) rather than force `-D`. Granted to `code` mode in full; `debug` mode gets only the non-destructive pair (`git_branch`/`git_checkout`) alongside its existing `git_status`/`git_diff`.
- **Permission-prompt messaging for the two genuinely destructive new operations**: `git_reset --hard` and `git_push --force` now render a distinct `⚠ DESTRUCTIVE: ...` description explaining exactly what will be lost, instead of both falling into the same generic "Tool: git_reset" text every other tool call not yet given a specific `buildDescription()` case gets. Every git tool remains gated by the existing generic `/^git_/` "prompt" rule — no rule-table changes were needed, only the description shown in that prompt.

**Test battery: 87 new tests** — `tests/unit/git-tools-security.test.ts` (26, new — live-PoC-style injection-canary tests for every fixed `builtin.ts` handler, using the exact "craft a payload that creates a real file, then assert it wasn't created" pattern that found the `git_commit` bug, plus functional regression coverage for legitimate usage), `tests/unit/git-operations.test.ts` (24, new — the six newly-wired tools against real temp git repos, including push/pull against a real local bare remote and a real force-push-over-diverged-history scenario), `tests/unit/code-search-grep.test.ts` (13, new), `tests/unit/formatter.test.ts` (4, new), `tests/unit/permission-system.test.ts` (+12 — the new destructive-operation description messaging), `tests/unit/tools.test.ts` (+6 — registration/tool-set/dedup regression), `tests/e2e/agent-loop.test.ts` (+2 — a real `git_commit` injection attempt and a real `git_branch` creation, both driven through actual LLM-output tool-call parsing against a real git repo, not direct handler calls).

## Sandbox boundary hardening (path traversal + apply-command rollback gap)

While fixing the git command-injection issues above, `file-system.ts`'s `resolveOutputPath()` — the function `file_copy`/`file_move`/`directory_create` use to resolve a relative path against the "sandboxed" output directory — turned out to have a real, live-reproducible path-traversal hole: `join(outputDir, relativePath)` normalizes `..` segments syntactically but never clamps the result to stay inside `outputDir`. **Confirmed with a live PoC**: `directory_create({ path: "../../../../tmp/ESCAPED_SANDBOX_DIR" })` created a real directory directly in the user's home folder, entirely outside any project directory.

- **`resolveOutputPath()` now rejects any relative path whose resolved form escapes `outputDir`**, throwing an error the existing per-handler `try/catch` already turns into a clean `{success:false}` result — no new error-handling plumbing needed. Also fixed a related false-positive: the old containment check (`relativePath.startsWith(outputDir)`) was a raw string-prefix test, so a sibling directory merely sharing `outputDir` as a text prefix (e.g. `"output-old"` when `outputDir` is `"output"`) was wrongly treated as already being inside the sandbox. Now a proper path-boundary check (`=== outputDir` or starts with `outputDir + sep`).
- **`applyDiff()` (`diff-merge.ts`, the `apply` command's core write path) had zero rollback coverage** — it overwrites the real source tree in bulk, across every changed file in one shot, which is exactly the highest-blast-radius write in the whole tool layer, yet never went through the `RollbackManager` safety net wired into `file_write`/`file_delete`/`file_move` two phases ago. Added the same `snapshot()`-before-overwrite call; `coding-agent apply` now prints a hint that `coding-agent rollback <path>` can undo any individual file it touched.
- Added `resetTaskManager()` (mirroring the existing `resetRollbackManager()` test-seeding pattern) — needed to test `resolveOutputPath()` against a controlled sandbox root rather than the real project directory, and incidentally closes `task-manager.ts`'s prior zero-test-coverage gap.

**Test battery: 53 new tests** — `tests/unit/file-system-traversal.test.ts` (14, new — the live-PoC-style traversal-blocked-for-real assertions across `directory_create`/`file_copy`/`file_move`, plus the sibling-directory false-positive regression), `tests/unit/diff-merge.test.ts` (20, new — `generateUnifiedDiff`/`applyDiff`/`generateSimpleDiff`, including a full generate→apply→restore round trip and a fresh-process rollback-manager scenario), `tests/unit/task-manager.test.ts` (18, new — previously zero coverage), `tests/e2e/agent-loop.test.ts` (+1 — a real `directory_create` traversal attempt driven through actual LLM-output tool-call parsing against a real sandboxed cwd, not a direct handler call).

## AgentSpawner hardening (mode-pinning bug + memory leak)

`AgentSpawner.ts` — the actual execution engine behind `run`/`debug`/`test`/`review`/`simplify` (all via `executeTask()`) and every interactive-mode command — had **zero test coverage**, despite being the real path every CLI invocation goes through (the e2e tests built in earlier phases all drive `UniversalAgent.execute()` directly, never through `AgentSpawner`). Auditing it for the same class of issue found in every prior phase this session surfaced a real, live-reproducible bug in the *routing* logic itself, not just the tool layer underneath it.

- **Mode-pinning bug: `debug`/`test`/`review` (and even `code`) agents spawned via `AgentSpawner` were not reliably running in the mode they were explicitly invoked for.** `registerAgentFactories()` constructed `new UniversalAgent()` (no mode argument) and called `.setMode(mode)` afterward — but only the *constructor* sets `modeExplicitlySet = true`; `.setMode()` alone does not. `UniversalAgent.execute()` treats an agent with `modeExplicitlySet = false` as never having been pinned, and silently re-detects the mode from `task.description` the instant `task.metadata.mode` isn't set — which none of `run`/`debug`/`test`/`review`/`simplify` ever set. **Confirmed live**: spawning a `"debug"` agent for the task *"please analyze code quality and suggest improvements"* (no debug-specific keywords) executed in **`review`** mode instead — wrong system prompt, wrong tool set (review mode doesn't even have `file_write`). This defeated the entire purpose of having dedicated `debug`/`test`/`review` commands. Fixed by passing the mode directly to the constructor (`new UniversalAgent(mode)`) instead of constructing bare and calling `setMode()` after.
- **Unbounded memory leak**: `spawn()`+`execute()` never removes finished agents from the `agents` map, and neither `executeTask()` nor interactive mode's per-turn task execution ever calls `destroy()`. A one-shot CLI invocation doesn't notice (the process exits immediately), but interactive mode spawns one full agent instance — conversation history and all — through this exact singleton on every user turn, for the lifetime of a potentially long-running session. Added `pruneFinishedAgents()` (called after every `execute()`), capping retained completed/failed agents at 20 and always evicting the oldest first; running/pending agents are never touched.
- **`getSpawnOptions()` — a fully-implemented, system-capability-aware timeout/parallelism calculator — had zero callers anywhere**, so every task always got the same fixed default regardless of actual system load. Wired it into both `executeTask()` and interactive mode's task-execution path.

**Test battery: 49 new tests**, all in new `tests/unit/agent-spawner.test.ts` — direct mode-pinning regression checks for every agent type (spawn-time state inspection, no LLM call needed), two real end-to-end proofs through `execute()` via the `FakeProvider` harness, capacity-limiting, the pruning/eviction behavior (including an oldest-evicted-first ordering check), `execute()`'s error/timeout/callback handling (using a monkey-patched never-resolving `agent.execute` to force a real timeout), `getSpawnOptions()`'s clamping math, and `executeTask()`'s command-routing + risk-population integration.
